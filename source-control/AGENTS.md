# Source Control

## Commit Attribution

Do not add attribution identifying the agent, model, or agent provider as
an author or co-author in commit messages. This includes `Co-Authored-By`
trailers and equivalent "generated by" or "assisted by" statements. Do not
alter existing human attribution.

## Staging Safety

- Before staging or committing, inspect both the working-tree changes and
  the existing staging area. Do not assume that pre-existing staged work
  belongs to the current task or is authorised for the requested commit.
- Stage only the intended changes. Prefer explicit paths or selected hunks
  over broad staging commands when unrelated changes are present. A file
  may contain both intended and unrelated edits; selecting its path alone
  does not establish that all its changes belong in the commit.
- Preserve unrelated staged and unstaged work. Do not unstage, overwrite,
  or include it merely to simplify a commit. If the requested changes
  cannot be isolated safely, ask how to proceed.
- Review the complete staged diff and file list before committing,
  including newly added files. Confirm that the content matches the
  authorised scope and intended logical commit; a diff summary alone is
  not sufficient. If unrelated staged work would be included, pause and
  agree a safe approach rather than committing it accidentally.
- After staging, confirm what is staged and what remains unstaged. After
  committing, verify the commit's actual contents and remaining working
  tree and staging state. Report discrepancies rather than silently
  discarding changes or rewriting the commit.

## Commit Scope

- Organise commits around coherent ideas, not arbitrary size limits.
  Separate unrelated changes, but keep related work together when that
  best explains the intent.
- For a substantial body of work, use commits to preserve a useful
  progression of ideas. Intermediate commits need not compile or pass all
  tests when separating an idea makes the history clearer and the project
  permits it. Make intentional intermediate limitations explicit.
- Validate the completed body of work appropriately. An intentionally
  incomplete intermediate commit does not justify leaving the final
  result unverified or concealing failures.
- If explaining a commit requires jumping between unrelated changes or
  several independent motivations, reconsider its scope. This is a signal
  to review the grouping, not a requirement to split every complex change.
- Plan useful commit boundaries as work progresses. Do not rewrite
  existing history merely to improve its presentation.

## Commit Messages

- Use Conventional Commits only when it is an established project
  convention. Check contributor guidance, commit-message tooling, and
  recent history. Otherwise, follow the project's existing message style;
  do not introduce Conventional Commits merely because this harness
  mentions them. If the evidence conflicts, ask before choosing a format.
- When Conventional Commits applies, read the
  [bundled specification](references/conventional-commits/specification.md).
  Follow the project's types, scopes, and restrictions. The upstream FAQ's
  suggestions about rebasing and squashing do not override the
  [History Preservation](#history-preservation) rules below.
- Aim to keep the first-line summary within 80 characters. Keep it concise
  and descriptive rather than filling the available space.
- Separate the summary from any message body with a blank line. Use the
  body for rationale and important context that does not fit the summary.
- Write for future maintainers investigating why a change exists. Explain
  its purpose, relevant context, and reasoning that is not apparent from
  the diff. Record important constraints and trade-offs where useful.
- Keep messages proportionate to the change. A short explanation can be
  sufficient; do not repeat the diff or add prose to satisfy a length
  quota. Use a body when the summary alone cannot preserve the context.
- Apply this guidance to new commits; do not rewrite existing history
  merely to adjust message length.

## History Preservation

- Do not rewrite source-control history unless the user explicitly
  instructs it. Permission to create commits does not authorise amending,
  rebasing, squashing, dropping, or otherwise replacing existing commits.
- Preserve the progression of the work so reviewers can see how it evolved.
  Use follow-up commits to correct earlier changes and revert commits to
  reverse them. A commit later reversed by another commit is valid history;
  do not rewrite history merely to hide a correction or abandoned approach.
- Updating a commit message rewrites history. Only do so with explicit user
  permission, on an unsigned commit owned by the user, and within the
  authorised scope. If ownership or permission is unclear, ask first.
- Do not modify other people's commits. Check the full set of commits an
  operation would replace, not just its target; rewriting an earlier commit
  can also replace descendant commits.
- Never remove or rewrite signed commits, strip their signatures, or
  replace them with unsigned or newly signed copies. A message-only edit
  changes the signed commit too. If an operation would affect a protected
  commit, report the conflict and use a non-rewriting alternative.

## Git Unreachable and Dangling Commits

- Do not create temporary commits or move references unnecessarily. Prefer
  ordinary follow-up commits over history-rewriting operations.
- Do not delete unreachable or dangling commit objects merely to obtain a
  clean diagnostic result. They may contain recoverable work and may
  predate the current task.
- Do not run pruning, reflog-expiry, or aggressive garbage-collection
  operations to remove such objects without explicit user authorisation.
- If an operation leaves commits unreachable, report what happened. Where
  those commits may contain work that should be retained, propose
  preserving them with a recovery reference before cleanup.
- Distinguish unreachable objects from repository corruption. Dangling
  commits alone do not indicate a damaged repository or require cleanup.

Dangling objects are a subset of unreachable objects. An unreachable
commit can still be referenced by another unreachable object; these rules
apply regardless of the diagnostic label.
